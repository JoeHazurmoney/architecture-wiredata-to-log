wd2l 1.2.0 changes what comes with each release, not how wd2l runs:
* every component in the SBOMs has a supplier and a hash;
* the RPMs and the Python package get SBOMs of their own;
* a page shows all of it, offline;
* two scanners report what each one covered;
* a comparison image shows what the minimal base leaves out;
* the dashboard's status, pipeline and segment panels show their values again.

wd2l's code, settings, wire format, auditd rules and alerts are those of 1.1.0. The dashboard is
the one change to what the RPMs install. It's the code of 1.2.0rc2, which was released, verified
offline, and run on the test hosts, as 1.2.0rc1 was before it. Upgrade from 1.1.0 in a planned
window, as "Upgrading" says.

## What changed since 1.1.0

**The SBOMs**
* **Every component names its supplier,** by a rule on its package ID. For example, Red Hat for
  the base's RPMs, and the wd2l project for wd2l. Before, every component said `NOASSERTION`. A
  component that no rule covers stops the release.
* **Every component has its own SHA-256:**
  * each RPM in the image, its header's digest, which `rpm -q --qf '%{SHA256HEADER}'` also gives;
  * wd2l, the SHA-256 of the wheel it was installed from.
* **wd2l's own files are all tied to wd2l,** each checked against the wheel's `RECORD`. Before,
  only its 3 launchers were.
* **The image is named as it's published** (`ghcr.io/joehazurmoney/wd2l` and the version), and
  the SBOM's author is the wd2l project. The same image always gets the same SPDX namespace.
* **SBOMs of the RPMs and the Python package,** each in SPDX and CycloneDX:
  `wd2l-<version>-rpms-el9`, `-rpms-el10` and `-python`.
  * **The RPM SBOMs:**
    * each RPM's own digests;
    * each file it installs, with its SHA-256, checked against the RPM's header;
    * what it needs from the host, such as `python3 >= 3.9`, systemd and nftables. These are
      listed as required, not shipped.
  * **The Python SBOM:** the wheel and the sdist, with their files, and the pinned tools that
    built them.

**A page for reading them: `wd2l-<version>-sbom.html`**
* **It opens in any browser, offline,** and loads nothing from the network.
* **It has a tab** for each platform's image, the comparison image, each RPM set and the Python
  package, with a table comparing them.
* **For each component, it shows** its files with their SHA-256, and the known vulnerabilities
  each scanner found.
* **It shows which of the fields an SBOM is expected to carry** are present.
* **It's a release file like the rest:** in the manifest and in the signed `SHA256SUMS`. The SPDX
  and CycloneDX files remain the record.

**Vulnerability scanning**
* **Each scan says what each scanner covered.** Grype's data covers the Hardened image's
  operating system. Trivy's doesn't, though it still scans the Python packages. A scan in which no
  scanner covers the operating system's packages now pauses for a security review.
* **Findings are merged across the scanners,** each naming the scanner that found it. A finding
  that one scanner reported and another, covering that package, didn't is listed for a person
  to look at.
* **Every warning a scanner or Syft gives is raised on the run.** Warnings that recur are in a
  reviewed list with a 90-day expiry. They're shown as expected, and raised again once their
  review lapses.

**A comparison image on UBI 9 (not for deployment)**
* **`ghcr.io/joehazurmoney/wd2l-ubi9`** (linux/amd64) is the same wd2l, built from the same wheel,
  on Red Hat's general-purpose UBI 9 base. It shows what the Hardened base leaves out.
* **Built from 1.1.0's wheel:**
  * 207 components, against the Hardened image's 65;
  * 535 known vulnerabilities, against 7;
  * a shell and a package manager;
  * 315 MB unpacked, against 127 MB.
* **It's built, scanned, signed and verified as the shipped image is,** and saved as
  `wd2l-<version>-image-ubi9-amd64-oci.tar`. It is not hardened and not FIPS.
* **Its findings are shown,** in `wd2l-<version>-vuln-summary-ubi9-amd64.md` and on the SBOM
  page, and never hold up a release.
* **Deploy the Hardened FIPS image, `ghcr.io/joehazurmoney/wd2l`, as before.**

**The image**
* It's built on newer digests of the same base images (`hi/python:3.12-fips` and its builder).
  The only package that changed is `sqlite-libs` (3.54.0 to 3.54.1). The base adds no known
  vulnerability and removes none.

**The state-of-health dashboard**
* **Its latest-value panels show data again.** Transfer status, Where and why, Open gap events,
  Time, Pipeline and the six segment panels were empty on a running system: UNKNOWN, `###`, or
  "No search results returned".
  * **Why:** each reads the latest health record from one shared search, and that search
    returned raw events, which pass on only the fields the search names. So none of the record's
    fields reached those panels.
  * **The fix:** the shared search now ends in `| fields *` (#203).
  * **Every release before 1.2.0rc2** shipped the dashboard that way.
* **The file:** `wd2l-health-dashboard.json`, installed by the `wd2l-receiver` RPM in
  `/usr/share/wd2l/splunk/`. An installed copy doesn't change by itself: see "Upgrading".

## Verifying it

```bash
python3 wd2l-1.2.0-verify-release.py --key cosign.pub --image-tar wd2l-1.2.0-image-<arch>-oci.tar
```

Use a `cosign.pub` obtained from a trusted channel. `docs/releasing.md` lists each check
separately. The comparison image's tar is checked the same way, with `--image-tar
wd2l-1.2.0-image-ubi9-amd64-oci.tar`.

## Upgrading

* **From 1.1.0 or 1.2.0rc1:**
  * run `dnf upgrade`, then stop and start as `docs/planned-downtime.md` says;
  * on container hosts, bring in the 1.2.0 image and update the `Image=` line;
  * in the SIEM, replace the dashboard with the new file: in Splunk, open "wd2l state of
    health", **Edit**, **Source**, paste `/usr/share/wd2l/splunk/wd2l-health-dashboard.json`,
    and save. If you adapted the dashboard, add `| fields *` to the end of its two
    `… type=health | head 1` searches instead.

  Nothing else changed: the settings, the wire format, the auditd rules and the alerts are
  1.1.0's.
* **From 1.2.0rc2:** run `dnf upgrade`, bring in the 1.2.0 image and update the `Image=` line,
  then stop and start as `docs/planned-downtime.md` says. The dashboard is rc2's.
* **From earlier releases:** follow the 1.1.0 notes, then the above.
